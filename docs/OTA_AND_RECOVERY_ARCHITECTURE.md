# Архитектура OTA, подсистемы аварийного восстановления и специфика USB-Locked устройств Xteink X4 Pro (BookPoint OS)

## 1. Введение и архитектурные цели

Настоящий документ представляет собой исчерпывающее нормативное и техническое описание подсистемы беспроводного обновления (OTA), протокола взаимодействия с заводскими сервисами Xteink, микро-загрузчика аварийного восстановления **Escape Hatch**, алгоритмов переключения разделов загрузки (`otadata`), механизма прошивки с карты памяти microSD, а также архитектурных решений по защите от окирпичивания электронных книг **Xteink X4 Pro** с аппаратной блокировкой USB-интерфейса.

Документ составлен на основе исследования схемотехники Xteink X4 Pro, анализа реверс-инжиниринга трафика заводских серверов Xteink (`api-prod.xteink.cn` / `api-prod.xteink.cc`), аудита исходного кода инструментов `xteink-unlocker`, `crosspoint-tools` (issue #41), PR #1990 `crosspoint-reader`, а также кодовой базы BookPoint OS (`src/`).

Целевая платформа спецификации: **Флагманский ридер Xteink X4 Pro (ESP32-S3)**. Поддержка устаревших плат предыдущих поколений (X3/X4 на базе ESP32-C3) полностью исключена из архитектурного скоупа ввиду принципиальных аппаратных различий и перехода проекта на моноплатформенную базу X4 Pro.

## 2. Аппаратная платформа Xteink X4 Pro и феномен «USB-Locked»

### 2.1. Спецификация аппаратной платформы (Hardware Ground Truth)

Ридер Xteink X4 Pro спроектирован на базе высокопроизводительной вычислительной платформы Espressif Systems:
* **Микроконтроллер (SoC):** ESP32-S3 (двухъядерный 32-битный процессор Xtensa LX7 с тактовой частотой 240 МГц, векторными инструкциями и поддержкой аппаратного шифрования).
* **Флеш-память:** 16 МБ SPI Flash (Quad/Octal SPI, разметка 16 МБ).
* **Оперативная память:** 8 МБ Octal PSRAM (OPI, высокая пропускная способность для кадровых буферов 800x480 и векторных шрифтов).
* **Дисплей E-Ink:** 800x480 точек (монохромный и 4 градации серого), контроллеры SSD1677 / UC8279, подключение по шине SPI (CS=GPIO 13, DC=GPIO 18, RST=GPIO 14, BUSY=GPIO 6).
* **Сенсорный экран:** Goodix GT911 (емкостный мультитач) на шине I2C 0 (адрес `0x5D`, INT=GPIO 10, RST=GPIO 4, powerEnable=GPIO 2 active-LOW).
* **Аппаратные часы реального времени (RTC):** NXP/Belling BM8563 (PCF8563-совместимый чип) на шине I2C 0 (адрес `0x51`).
* **Монитор аккумулятора (Fuel Gauge):** CellWise CW2017 на шине I2C 0 (адрес `0x63`).
* **Двухканальная подсветка (Frontlight):** 2-канальный LEDC PWM 25 кГц с логарифмической гамма-коррекцией (Холодный канал = GPIO 8, Теплый канал = GPIO 9).
* **Слот MicroSD:** Нативный 1-битный SDMMC интерфейс (CLK=GPIO 41, CMD=GPIO 42, DAT0=GPIO 40, powerEnable=GPIO 5 active-LOW).
* **Физические кнопки управления:**
  * Правая кнопка (Right / Page Next): **GPIO 7** (active-LOW, внутренний `INPUT_PULLUP`).
  * Левая кнопка (Left / Page Prev): **GPIO 0** (active-LOW, **BOOT-STRAP PIN** микроконтроллера).
  * Кнопка питания (Power / Wakeup): **GPIO 3** (active-LOW, аппаратная защелка питания и источник пробуждения из глубокого сна).

### 2.2. Природа аппаратной блокировки USB («USB-Locked»)

Массовые розничные партии ридеров Xteink X4 Pro, поставляемые с китайских торговых площадок (Taobao, AliExpress, 1688), имеют жесткую заводскую блокировку передачи данных по интерфейсу USB:
1. **Физический разрыв сигнальных линий:**  
   Дифференциальные линии данных `D+` и `D-` порта USB Type-C физически не подключены к контактным площадкам ESP32-S3 (GPIO 19 и GPIO 20). На плате распаяны исключительно цепи питания `VBUS` (+5V) и общий провод `GND`, либо установлен зарядный контроллер, изолирующий сигнальные контакты разъема.
2. **Поведение на стороне операционной системы:**  
   При подключении устройства комплектным или качественным дата-кабелем к персональному компьютеру:
   * **Windows:** В Диспетчере устройств появляется ошибка `Код 43: Сбой запроса дескриптора устройства (Unknown USB Device / Device Descriptor Request Failed)`. Устройство не способно ответить на базовый пакет Setup транзакции перечисления USB.
   * **Linux:** Ядро регистрирует сбой в кольцевом буфере `dmesg`:
     ```text
     [ 1420.112034] usb 1-1: new full-speed USB device number 12 using xhci_hcd
     [ 1425.232045] usb 1-1: device descriptor read/64, error -110
     [ 1430.480039] usb 1-1: device descriptor read/64, error -71
     [ 1430.592041] usb 1-1: device not accepting address 12, error -71
     [ 1430.704044] usb 1-1: unable to enumerate USB device
     ```

### 2.3. Критические последствия для архитектуры отказоустойчивости

Аппаратная блокировка USB коренным образом меняет парадигму разработки встроенного ПО для Xteink X4 Pro:
1. **Полная недоступность низкоуровневых интерфейсов прошивки:**  
   WebSerial, ESP Web Tools, классический `esptool.py`, USB CDC Serial и аппаратный JTAG через USB-разъем **не функционируют в принципе**. Устройство невозможно перепрошить через проводной интерфейс без физического вскрытия.
2. **Единственные каналы обновления и восстановления:**  
   Жизнеспособность устройства опирается исключительно на два изолированных механизма:
   * **Беспроводное обновление по воздуху (Wi-Fi 802.11 b/g/n OTA);**
   * **Автономное аварийное обновление с карты памяти microSD.**
3. **Недопустимость регрессий и изоляции прошивки (Урок Papyrix):**  
   В неофициальных сборках (например, в стороннем форке Papyrix) разработчики вырезали модуль Wi-Fi и код OTA-обновления ради экономии оперативной памяти и места во флеше под встроенные шрифты. На USB-locked ридерах установка такой прошивки приводила к **необратимому окирпичиванию устройства**:
   * По USB прошить нельзя (линии физически отрезаны).
   * По Wi-Fi запросить обновление невозможно (сетевой стек удален).
   * Если прошивка повреждала таблицу `otadata` или не содержала кода чтения MicroSD, ридер превращался в "мертвый груз".
   * Единственный способ возврата к жизни окирпиченного ридера — механическое вскрытие корпуса, размягчение клея E-Ink экрана ацетоном в течение 2-3 часов, снятие хрупкой стеклянной подложки дисплея, выпаивание аккумулятора и подключение внешнего программатора с прищепкой SOIC-8 (CH341A) напрямую к выводам микросхемы SPI Flash.

**Императив архитектуры BookPoint OS:**  
Подсистема OTA и аварийный загрузчик Escape Hatch являются жизненно важными элементами системы. Их работоспособность, неизменность схемы разделов и автономность гарантируются на архитектурном уровне.

## 3. Разметка флеш-памяти и архитектура двойного слота (Dual-Slot Boot)

### 3.1. Структура таблицы разделов (`partitions.csv`)

Для микроконтроллера ESP32-S3 с объемом флеш-памяти 16 МБ (16,777,216 байт) принята симметричная схема разделов, зафиксированная в файле `src/partitions.csv`:

```csv
# Name,   Type, SubType, Offset,   Size,     Flags
nvs,      data, nvs,     0x9000,   0x5000,
otadata,  data, ota,     0xe000,   0x2000,
app0,     app,  ota_0,   0x10000,  0x640000,
app1,     app,  ota_1,   0x650000, 0x640000,
spiffs,   data, spiffs,  0xc90000, 0x360000,
coredump, data, coredump,0xFF0000, 0x10000,
```

#### Детальная карта памяти 16 МБ Flash:

| Имя раздела | Тип / Подтип | Смещение (Offset) | Размер (HEX) | Размер (Десятичный) | Назначение раздела |
|---|---|---|---|---|---|
| **Bootloader** | - | `0x000000` | `0x008000` | 32 КБ | Заводской 2nd-stage bootloader ESP-IDF |
| **Partition Table** | - | `0x008000` | `0x001000` | 4 КБ | Бинарная таблица разделов flash |
| **nvs** | `data / nvs` | `0x009000` | `0x005000` | 20 КБ | Энергонезависимое хранилище NVS (Wi-Fi калибровки, ключи) |
| **otadata** | `data / ota` | `0x00E000` | `0x002000` | 8 КБ (2 сектора) | Двойной дескриптор выбора активного OTA-слота (Ping-Pong) |
| **app0** (`ota_0`) | `app / ota_0` | `0x010000` | `0x640000` | 6.25 МБ (6,553,600 Б) | **Escape Hatch Recovery Bootloader** (аварийный слот) |
| **app1** (`ota_1`) | `app / ota_1` | `0x650000` | `0x640000` | 6.25 МБ (6,553,600 Б) | **BookPoint OS** (основная рабочая операционная система) |
| **spiffs** | `data / spiffs` | `0xC90000` | `0x360000` | 3.375 МБ (3,538,944 Б) | Встроенные ресурсы (заставки сна, словари, системные шрифты) |
| **coredump** | `data / coredump` | `0xFF0000` | `0x010000` | 64 КБ | Сохранение дампов регистров и стека при системных паниках |

### 3.2. Роль и математика раздела `otadata`

Раздел `otadata` расположен по смещению `0x00E000` и имеет размер ровно 8192 байта, что соответствует двум физическим секторам SPI Flash (по 4096 байт каждый):
* **Сектор 0:** Смещение `0x0000` относительно начала `otadata` (абсолютный адрес `0x00E000`).
* **Сектор 1:** Смещение `0x1000` относительно начала `otadata` (абсолютный адрес `0x00F000`).

В начале каждого сектора располагается 32-байтный дескриптор `esp_ota_select_entry_t` (`SelectEntry`), выровненный по границе 4 байт:

```cpp
struct __attribute__((packed)) SelectEntry {
  uint32_t ota_seq;       // Монотонно возрастающий счетчик последовательности
  uint8_t  seq_label[20]; // Служебное поле, заполненное байтами 0xFF
  uint32_t ota_state;     // Состояние образа (0 = ESP_OTA_IMG_NEW)
  uint32_t crc;           // Контрольная сумма CRC32-LE от поля ota_seq (4 байта)
};
static_assert(sizeof(SelectEntry) == 32, "SelectEntry must be exactly 32 bytes");
```

#### Математический алгоритм выбора слота загрузчиком ESP-IDF:
1. Загрузчик считывает оба дескриптора из Сектора 0 и Сектора 1.
2. Для каждого сектора вычисляется контрольная сумма:
   $$\text{CRC32-LE}(\text{ota\_seq}) \quad \text{с начальным значением } \text{0xFFFFFFFF}$$
   Контрольная сумма считается строго по первым 4 байтам структуры (`ota_seq`).
3. Секторы с нарушенной контрольной суммой, незаписанные секторы (`ota_seq == 0xFFFFFFFF`), а также записи в состояниях `ESP_OTA_IMG_INVALID` (3) или `ESP_OTA_IMG_ABORTED` (4) отбрасываются.
4. Из оставшихся валидных секторов выбирается сектор с **наибольшим значением `ota_seq`**.
5. Целевой раздел загрузки вычисляется по формуле:
   $$\text{Partition Index} = (\text{ota\_seq} - 1) \pmod{\text{NUM\_OTA\_PARTITIONS}}$$
   Для двух разделов (`NUM_OTA_PARTITIONS = 2`):
   * Если `ota_seq` нечетный ($1, 3, 5, \dots$), загружается слот **0** (`app0` / `ota_0`).
   * Если `ota_seq` четный ($2, 4, 6, \dots$), загружается слот **1** (`app1` / `ota_1`).

#### Алгоритм атомарного переключения слотов (`ota_boot::switchTo`):
Для безопасного переключения без риска повреждения данных при внезапном обесточивании запись всегда производится в **неактивный** сектор:
1. Определяется текущий активный сектор `activeIdx` (0 или 1) и текущее максимальное значение `activeSeq`.
2. Вычисляется индекс целевого раздела:
   $$\text{destOtaIdx} = \text{dest}->\text{subtype} - \text{ESP\_PARTITION\_SUBTYPE\_APP\_OTA\_0}$$
3. Находится наименьшее число $\text{newSeq} > \text{activeSeq}$, удовлетворяющее условию:
   $$(\text{newSeq} - 1) \pmod 2 == (\text{destOtaIdx} \pmod 2)$$
4. Формируется структура `SelectEntry`:
   * `next.ota_seq = newSeq;`
   * `memset(next.seq_label, 0xFF, sizeof(next.seq_label));`
   * `next.ota_state = kOtaImgNew;` (0)
   * `next.crc = computeSeqCrc(newSeq);`
5. Выбирается неактивный сектор: $\text{targetSlot} = 1 - \text{activeIdx}$.
6. Выполняется физическое стирание неактивного сектора:
   `esp_partition_erase_range(otadata, targetSlot * 4096, 4096)`.
7. Выполняется запись 32 байт новой структуры:
   `esp_partition_write(otadata, targetSlot * 4096, &next, sizeof(next))`.

Благодаря механизму двух секторов, если питание устройства прервется в момент стирания или записи неактивного сектора, активный сектор останется неповрежденным, и загрузчик продолжит штатно запускать предыдущую работоспособную прошивку.

## 4. Автономный микро-загрузчик Escape Hatch

### 4.1. Назначение и изоляция

**Escape Hatch** — это компактная автономная микро-операционная система восстановления, которая развертывается в разделе `app0` (`ota_0`, смещение `0x010000`).

Размер бинарного образа Escape Hatch составляет всего **~518 КБ** (против 5.5–6.0 МБ у полной BookPoint OS). Компактный размер обеспечивает:
* Гарантированную установку через заводской апдейтер XTOS V7.4.4 без переполнения оперативной памяти;
* Минимальное время старта и низкое энергопотребление;
* Полную независимость от пользовательских настроек, базы данных библиотеки, шрифтовых файлов и сетевого стека.

### 4.2. Архитектура микро-загрузчика

Escape Hatch содержит только необходимый минимум драйверов для спасения устройства:
* Ядро FreeRTOS с базовым планировщиком;
* Легковесный драйвер дисплея E-Ink SSD1677 / UC8279 (поддержка монохромной отрисовки аварийного меню);
* Драйвер нативного 1-битного интерфейса SDMMC для работы с картами MicroSD;
* Низкоуровневый модуль работы со SPI Flash (`spi_flash`, `esp_partition`) и модуль переключения `otadata`.

### 4.3. Процедура аварийного обновления с MicroSD (`update.bin`)

При запуске Escape Hatch выводит на дисплей диалоговое окно аварийного восстановления и запускает опрос карты памяти MicroSD:
1. **Поиск файла:** Выполняется поиск файла `update.bin` строго в корневом каталоге карты памяти (файловая система FAT32).
2. **Многоуровневая валидация образа:** До стирания флеш-памяти файл подвергается проверке (`validateImageFile`):
   * **Магический байт:** Байт со смещением 0 обязан быть равен `0xE9` (`ESP_IMAGE_HEADER_MAGIC`).
   * **Целевой чип (Chip ID):** Байты 12-13 заголовка сравниваются с идентификатором ESP32-S3 (`0x0009`).
   * **Тег целевой платы:** Потоковое сканирование сигнатуры платы в образе: `CROSSPOINT-BOARD-V1:x4pro;`. Попытка прошить образ от других устройств отсекается.
   * **Целостность данных:** Потоковый расчет контрольной суммы XOR (seed `0xEF`) и сверка 32-байтного SHA-256 хеша в конце образа.
3. **Запись прошивки:** Валидный образ записывается блоками по 4 КБ в раздел `app1` (`ota_1`, смещение `0x650000`).
4. **Финализация:** Вызывается `ota_boot::switchTo(app1)`, переключающий `otadata` на слот 1.
5. **Перезапуск:** Выполняется контролируемый перезапуск `esp_restart()`, после чего ридер загружает обновленную BookPoint OS.

## 5. Аппаратный загрузочный перехватчик (`checkBootCombo`)

### 5.1. Точка входа в `src/main.cpp`

Штатный вторичный загрузчик ESP-IDF не поддерживает чтение пользовательских кнопок. Он безусловно запускает тот раздел, на который указывает `otadata`. Следовательно, аппаратный перехват аварийной ситуации обязан осуществляться **первой инструкцией** функции `setup()` в `src/main.cpp`:

```cpp
void setup() {
  freeink::recovery::checkBootCombo(); // Строка 1: Аппаратный аварийный перехват
  BoardConfig::holdPowerRails();        // Строка 2: Удержание питания аппаратных шин
  ...
```

Такое размещение гарантирует, что если основная прошивка содержит ошибку в инициализации дисплея, графической подсистемы, драйвера шрифтов или пользовательских настроек, удерживание кнопки на старте переключит устройство в Escape Hatch **до того**, как проблемный код успеет выполниться или вызвать панику ядра.

### 5.2. Аппаратный выбор кнопки для Xteink X4 Pro

На плате Xteink X4 Pro выведены три цифровые кнопки:
* **Кнопка Power (GPIO 3):** Подключена к цепи аппаратного контроллера питания и пробуждения. Не подходит в качестве изолированного комбо-триггера, так как она зажимается при каждом обычном включении устройства.
* **Левая кнопка (GPIO 0):** **КРИТИЧЕСКИ ОПАСНА!** Вывод GPIO 0 является аппаратным strapping-пином микроконтроллера ESP32-S3. Если удерживать кнопку, подключенную к GPIO 0, во время сброса или подачи питания, ROM-загрузчик ESP32-S3 переходит в режим загрузки прошивки по UART/USB (**ROM Download Mode**). На USB-locked ридере это приводит к полному зависанию устройства с черным экраном до полного разряда аккумулятора!
* **Правая кнопка (GPIO 7 / Page Down):** **ИДЕАЛЬНЫЙ ВЫБОР**. Вывод GPIO 7 является стандартным цифровым вводом/выводом без strapping-функций. Кнопка замыкает пин на землю (GND). При настройке внутреннего подтягивающего резистора `INPUT_PULLUP` ненажатая кнопка считывается как логическая `1` (HIGH), а нажатая — как логический `0` (LOW).

### 5.3. Временная диаграмма и аппаратная фильтрация дребезга

Для обеспечения мгновенной загрузки в нормальном режиме и защиты от ложных срабатываний реализована двухуровневая логика опроса:

```cpp
bool comboHeld() {
  const gpio_num_t kRightPin = GPIO_NUM_7;
  pinMode(kRightPin, INPUT_PULLUP);
  delayMicroseconds(50); // Время зарядки паразитной емкости вывода

  // БЫСТРЫЙ ПУТЬ (Fast-path): Нормальная загрузка
  // Если кнопка не нажата, выход происходит менее чем за 100 микросекунд.
  if (digitalRead(kRightPin) == HIGH) {
    return false;
  }

  // ФИЛЬТРАЦИЯ ДРЕБЕЗГА (Debounce Window):
  // Требуется подтверждение удержания: 7 последовательных чтений LOW с шагом 6 мс (~42 мс).
  constexpr int kRequiredSamples = 7;
  int consecutive = 0;
  for (int i = 0; i < 12; ++i) {
    if (digitalRead(kRightPin) == LOW) {
      if (++consecutive >= kRequiredSamples) {
        return true; // Надежно зажата
      }
    } else {
      consecutive = 0;
      return false; // Случайная помеха или отпускание
    }
    delay(6);
  }
  return false;
}
```

* **Нормальная загрузка:** Время выполнения проверки составляет `< 0.1 мс`. Задержка включения абсолютно неощутима для пользователя.
* **Аварийный запуск:** Пользователь зажимает Правую кнопку и нажимает кнопку включения питания. За время 30–50 мс фильтр подтверждает непрерывное удержание и активирует переход в recovery.

### 5.4. Требования безопасности при переключении

Функция `checkBootCombo()` выполняет строгую проверку условий перед модификацией флеш-памяти:
1. **Поиск раздела recovery:** Находится раздел `ota_0` (`esp_partition_find_first(ESP_PARTITION_TYPE_APP, ESP_PARTITION_SUBTYPE_APP_OTA_0, nullptr)`). Если раздел отсутствует, переключение не производится.
2. **Защита от бесконечного цикла перезагрузок:** Опрашивается текущий исполняемый раздел:
   ```cpp
   const esp_partition_t* running = esp_ota_get_running_partition();
   if (running && running->address == hatch->address) {
     return; // Устройство уже исполняет код из ota_0! Повторный рестарт блокируется.
   }
   ```
3. **Проверка валидности исполняемого образа (Magic 0xE9):**  
   Чтение первого байта раздела `ota_0`:
   ```cpp
   uint8_t magic = 0;
   if (esp_partition_read(hatch, 0, &magic, sizeof(magic)) != ESP_OK || magic != 0xE9) {
     return; // В разделе ota_0 стертая флеш (0xFF) или мусор. Переключение отменяется.
   }
   ```
4. **Атомарное переключение и перезагрузка:** Если все проверки успешны, вызывается `ota_boot::switchTo(hatch)`, выдерживается пауза 50 мс для завершения операций контроллера флеш-памяти, и вызывается `esp_restart()`.

## 6. Программный вход в режим восстановления из интерфейса (UI Entry Point)

Помимо аппаратной кнопки на старте, BookPoint OS предоставляет прозрачный интерфейс для перехода в режим Escape Hatch прямо из настроек операционной системы.

### 6.1. Размещение в меню настроек (`SettingsActivity`)

Пункт меню размещается в корневом разделе настроек системы:
* **Категория:** «Система» (`STR_CAT_SYSTEM`, карточка 4 на главном хабе / вкладка 3).
* **Список настроек:** `systemSettings` (а также дублируется в подменю `systemUpdateLanguageSettings` рядом с «Проверить обновления» и «Обновление прошивки с SD»).
* **Действие:** `SettingAction::RecoveryEscapeHatch`.
* **Локализация пунктов меню:**
  * Русский язык (`russian.yaml`):  
    `STR_RECOVERY_ESCAPE_HATCH`: «Режим восстановления (Escape Hatch)»  
    `STR_RECOVERY_ESCAPE_HATCH_PROMPT`: «Перезагрузить устройство в аварийный загрузчик Escape Hatch?»  
    `STR_RECOVERY_ESCAPE_HATCH_FAILED`: «Не удалось переключиться: раздел повреждён или отсутствует»
  * Английский язык (`english.yaml`):  
    `STR_RECOVERY_ESCAPE_HATCH`: «Recovery Mode (Escape Hatch)»  
    `STR_RECOVERY_ESCAPE_HATCH_PROMPT`: «Reboot device into Escape Hatch recovery loader?»  
    `STR_RECOVERY_ESCAPE_HATCH_FAILED`: «Failed to switch: partition is invalid or missing»

### 6.2. Модальный диалог подтверждения

Для исключения случайного нажатия при сенсорном или кнопочном управлении вызов функции обязательно защищен модальным диалоговым окном подтверждения (`OptionPopup` или `ConfirmationActivity`).

Пользователю отображается предупреждающий запрос с двумя кнопками:
* `[ Отмена ]` — закрывает окно без изменений состояния системы;
* `[ Подтвердить ]` — запускает процедуру переключения слота и перезагрузки.

### 6.3. Алгоритм выполнения программного перехода (`triggerRecoveryReboot`)

```cpp
bool SettingsActivity::triggerRecoveryReboot() {
#if defined(ESP_PLATFORM) || defined(ARDUINO_ARCH_ESP32)
  // 1. Поиск раздела ota_0
  const esp_partition_t* hatch =
      esp_partition_find_first(ESP_PARTITION_TYPE_APP, ESP_PARTITION_SUBTYPE_APP_OTA_0, nullptr);
  if (!hatch) {
    LOG_ERR("RECOVERY", "Раздел ota_0 не найден в таблице разделов");
    return false;
  }

  // 2. Проверка текущего запущенного раздела
  const esp_partition_t* running = esp_ota_get_running_partition();
  if (running && running->address == hatch->address) {
    LOG_WRN("RECOVERY", "Устройство уже запущено из ota_0");
    return false;
  }

  // 3. Верификация сигнатуры ESP32 (0xE9)
  uint8_t magic = 0;
  if (esp_partition_read(hatch, 0, &magic, sizeof(magic)) != ESP_OK || magic != 0xE9) {
    LOG_ERR("RECOVERY", "Раздел ota_0 не содержит валидного исполняемого кода (magic=0x%02X)", magic);
    return false;
  }

  // 4. Прямое переключение otadata
  if (!ota_boot::switchTo(hatch)) {
    LOG_ERR("RECOVERY", "Ошибка записи otadata при переключении на ota_0");
    return false;
  }

  LOG_INF("RECOVERY", "Слот ota_0 успешно активирован. Сброс кэшей настроек и перезагрузка...");

  // 5. Корректное завершение работы системы
  SETTINGS.saveToFile(); // Фиксация всех несохраненных настроек на SD
  delay(100);            // Задержка на завершение операций файловой системы
  esp_restart();
  return true;
#else
  LOG_INF("RECOVERY", "[Simulator] Эмуляция перехода в Escape Hatch успешна");
  return true;
#endif
}
```

## 7. Безотказная финализация беспроводных обновлений (Bulletproof OTA & Issue #1918)

### 7.1. Анализ дефекта Issue #1918 в ESP-IDF

В стандартной реализации модуля обновления `src/network/OtaUpdater.cpp` загрузка прошивки завершается вызовом:
```cpp
esp_err = esp_ota_end(otaHandle);
...
esp_err = esp_ota_set_boot_partition(updatePartition);
```

#### Внутренний механизм сбоя:
1. Функция `esp_ota_set_boot_partition()` из состава ESP-IDF (`components/app_update/esp_ota_ops.c`) перед записью в `otadata` безусловно вызывает внутреннюю функцию `image_validate(partition, ESP_IMAGE_VERIFY)`.
2. Функция `image_validate()` вызывает `esp_image_verify()`, которая выполняет строгий аудит заголовков образа:
   * Проверка контрольных сумм сегментов памяти;
   * Сверка ревизии микросхемы и eFuse-блоков безопасности (`bootloader_common_check_efuse_blk_validity`);
   * Проверка таблиц сигнатур и метаданных сборки.
3. На ридерах Xteink X4 Pro заводской загрузчик и чипы имеют специфические конфигурации eFuse. Кроме того, сборки BookPoint OS могут модифицироваться скриптом `patch_firmware_image.py` для обеспечения совместимости с дисплейным контроллером.
4. В результате `esp_image_verify()` возвращает ошибку `ESP_ERR_IMAGE_INVALID`, которую `image_validate()` преобразует в `ESP_ERR_OTA_VALIDATE_FAILED`.
5. Функция `esp_ota_set_boot_partition()` аварийно завершает работу, **не внося изменений в раздел `otadata`**.
6. `OtaUpdater` возвращает ошибку `INTERNAL_UPDATE_ERROR`. Пользователь видит на экране сообщение о сбое обновления на отметке 99% или 100%, несмотря на то, что бинарный образ прошивки был полностью и без единой ошибки скачан и записан во флеш-память!

### 7.2. Архитектура отказоустойчивого переключения (Bulletproof Fallback)

Для стопроцентной гарантии применения валидных обновлений в `OtaUpdater.cpp` интегрирован двухуровневый алгоритм финализации, заимствованный из надежно зарекомендовавшего себя модуля `FirmwareFlasher.cpp`:

```cpp
#include "OtaBootSwitch.h"
...

  esp_err = esp_ota_end(otaHandle);
  if (esp_err != ESP_OK) {
    LOG_WRN("OTA", "esp_ota_end вернул статус: %s", esp_err_to_name(esp_err));
  }

  bool switchSuccess = false;

  // УРОВЕНЬ 1: Попытка штатного переключения через ESP-IDF API
  if (esp_err == ESP_OK) {
    esp_err_t set_err = esp_ota_set_boot_partition(updatePartition);
    if (set_err == ESP_OK) {
      LOG_INF("OTA", "esp_ota_set_boot_partition выполнен успешно");
      switchSuccess = true;
    } else {
      LOG_WRN("OTA", "esp_ota_set_boot_partition отклонил образ (%s); активация прямого переключения ota_boot::switchTo",
              esp_err_to_name(set_err));
    }
  }

  // УРОВЕНЬ 2: Резервное прямое переключение otadata (Иммунитет к Issue #1918)
  if (!switchSuccess) {
    uint8_t magic = 0;
    // Обязательная проверка наличия исполняемого кода ESP32 (0xE9) по смещению 0
    if (esp_partition_read(updatePartition, 0, &magic, sizeof(magic)) == ESP_OK && magic == 0xE9) {
      LOG_INF("OTA", "Сигнатура 0xE9 в целевом разделе подтверждена. Выполняется ota_boot::switchTo");
      switchSuccess = ota_boot::switchTo(updatePartition);
      if (switchSuccess) {
        LOG_INF("OTA", "Прямое переключение otadata успешно завершено -> раздел %s", updatePartition->label);
      } else {
        LOG_ERR("OTA", "Сбой прямого переключения otadata в ota_boot::switchTo");
      }
    } else {
      LOG_ERR("OTA", "В целевом разделе отсутствует сигнатура 0xE9 (считано: 0x%02X)", magic);
    }
  }

  if (!switchSuccess) {
    LOG_ERR("OTA", "Критический сбой: не удалось активировать новый раздел загрузки");
    return INTERNAL_UPDATE_ERROR;
  }

  LOG_INF("OTA", "Обновление микропрограммы успешно завершено");
  return OK;
```

### 7.3. Безопасность и верификация в процессе загрузки

Прямое переключение через `ota_boot::switchTo` не снижает уровень безопасности, поскольку валидация образа распределена по всему тракту приема данных:
1. **Фильтрация целевой платформы на лету (Board Tag Scanner):**  
   В процессе потоковой загрузки бинарных чанков модуль `board_tag::Scanner` производит поиск текстовой сигнатуры платы:
   `CROSSPOINT-BOARD-V1:x4pro;`
   Если пользователь случайно запустил обновление файлом от другой модели ридера, загрузка мгновенно прерывается вызовом `esp_ota_abort(otaHandle)` без повреждения flash.
2. **Проверка идентификатора чипа:**  
   По смещению 12 проверяется совпадение Chip ID (`0x0009` для ESP32-S3).
3. **Линкерная изоляция eFuse-проверок:**  
   В файле `platformio.ini` установлена директива компоновщика:
   `-Wl,--wrap=bootloader_common_check_efuse_blk_validity`
   которая подменяет функцию проверки блоков eFuse заглушкой, возвращающей `ESP_OK`. Это исключает ложные паники при штатных вызовах системных библиотек.

* **Размер заголовка контейнера:** Ровно 202 байта.
* **Сигнатура (Magic):** Первые 4 байта содержат ASCII-строку `XOTA` (`0x58 0x4F 0x54 0x41`).
* **Полезная нагрузка:** Начиная со смещения 202 (байт `0xCA`), располагается стандартный ESP32 Image Header, начинающийся с байта `0xE9`.

### 8.3. Архитектура утилиты Xteink Unlocker и обход сетевых конфликтов Windows

Утилита **Xteink Unlocker** выполняет разблокировку USB-locked ридеров методом локального перехвата DNS и HTTP трафика:
1. На ПК поднимается точка доступа Wi-Fi (подсеть `192.168.137.0/24`, адрес ПК `192.168.137.1`).
2. Встроенный DNS-сервер перенаправляет домены `api-prod.xteink.cn` и `api-prod.xteink.cc` на локальный IP `192.168.137.1`.
3. **Разрешение критического конфликта Windows WSAEACCES (Ошибка 10013):**  
   Системная служба Windows Time (**W32Time**) монопольно занимает UDP-порт 123. Локальный SNTP-сервер утилиты падает при попытке привязаться к порту 123. Решение заключается во временном отключении службы:
   ```powershell
   Stop-Service W32Time -Force
   sc.exe config W32Time start= disabled
   ```
4. **Обход ошибки нехватки памяти в стоковом обновлении XTOS V7.4.4:**  
   Стоковый апдейтер XTOS падает при попытке скачать файл размером более 5 МБ. Unlocker решает эту проблему в два этапа:
   * На первом этапе ридеру скармливается легковесный бинарник **Escape Hatch** размером 518 КБ (`.xota`), который стоковый загрузчик прошивает без ошибок в слот `ota_0`.
   * Ридер перезагружается в графический интерфейс Escape Hatch.
   * На втором этапе пользователь вставляет карту MicroSD с полной прошивкой BookPoint OS (`update.bin`), и Escape Hatch прошивает ее в слот `app1` (`ota_1`).

## 9. Матрица верификации и автоматизированное тестирование

Для обеспечения непрерывного контроля качества и предотвращения регрессий в подсистемах OTA и восстановления функционирует многоуровневый комплекс сквозного E2E-тестирования (`tests/e2e/run_e2e_tests.py` и `tests/e2e/contracts.py`).

### 9.1. Архитектурные поведенческие модели (`contracts.py`)

1. **`RecoveryBootModel` (Тестирование аппаратного перехвата):**
   * Моделирование физических состояний вывода GPIO 7 (лог. 0 / лог. 1).
   * Проверка алгоритма фильтрации дребезга: серия из 4 отсчетов LOW бракуется; серия из 5–7 отсчетов LOW активирует флаг комбо.
   * Проверка реакции на различные состояния раздела `ota_0`: стертый раздел (`0xFF`), некорректная сигнатура, совпадение адреса с текущим запущенным разделом.
2. **`UiRecoverySettingsModel` (Тестирование программного перехода):**
   * Моделирование навигации по иерархии меню (`SettingsActivity` -> категория «Система» -> пункт «Режим восстановления»).
   * Тестирование логики модального диалога: событие отмены оставляет систему в рабочем состоянии; событие подтверждения инициирует проверку `ota_0` и мягкий перезапуск.
3. **`BulletproofOtaModel` (Тестирование механизма финализации OTA):**
   * Программная модель расчета контрольной суммы CRC32-LE:
     $$\text{CRC32-LE}(\text{seq}) \quad \text{с полиномом } \text{0xEDB88320}$$
   * Моделирование чередования секторов `otadata` (0 -> 1 -> 0 -> 1) с проверкой монотонного роста `ota_seq`.
   * Моделирование сбоя `esp_ota_set_boot_partition` (ошибка Issue #1918) и верификация автоматического успешного переключения через `ota_boot::switchTo`.

### 9.2. Тестовые сценарии по уровням покрытия (Tiers)

## 10. Регламент действий инженера и аварийная инструкция пользователя

### 10.1. Правила разработки и сборки релизов
1. **Запрет на изменение разметки флеш:** Смещения `0x00E000` (`otadata`), `0x010000` (`app0`) и `0x650000` (`app1`) являются жестким аппаратным контрактом. Любое изменение `partitions.csv` приведет к несовместимости с заводским бутлоадером и окирпичиванию USB-locked устройств.
2. **Публикация бинарных артефактов на GitHub Releases:**  
   Каждый релиз BookPoint OS обязан содержать файл с каноническим именем `BookPoint_X.Y.Z_x4pro.bin` (а также символическую ссылку/копию `firmware-x4pro.bin` для автоматического OTA-модуля).
3. **Сохранение целостности сетевого стека:** Удаление Wi-Fi компонентов или OTA-клиента из прошивки строжайше запрещено.

### 10.2. Инструкция по аварийному восстановлению для владельцев Xteink X4 Pro

В случае любого критического сбоя, зацикливания перезагрузок или повреждения операционной системы:
1. **Подготовка карты памяти:**  
   * Отформатируйте карту MicroSD объемом до 32 ГБ в файловую систему FAT32.
   * Скачайте релизный файл прошивки `BookPoint_X.Y.Z_x4pro.bin`.
   * Переименуйте файл строго в `update.bin` и скопируйте его в **корневой каталог** карты памяти.
   * Вставьте карту памяти в слот выключенного ридера.
2. **Активация Escape Hatch по аппаратной кнопке:**  
   * Зажмите и удерживайте физическую **Правую кнопку** (кнопка перелистывания «Вперед / Вниз» на боковой грани).
   * Не отпуская Правую кнопку, зажмите кнопку **Включения питания** на 2–3 секунды до появления заставки или мигания экрана.
   * Отпустите обе кнопки.
3. **Процесс восстановления:**  
   * Ридер запустит микро-загрузчик Escape Hatch.
   * На экране отобразится статус чтения `update.bin` с MicroSD.
   * Нажмите подтверждение прошивки. Дождитесь заполнения шкалы прогресса записи Flash (около 30–45 секунд).
   * По окончании записи ридер автоматически перезагрузится в восстановленную BookPoint OS.
